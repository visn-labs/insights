# Milestone B, package 4: durable visual preparation and admission

Date: 18 October 2026. Status: implemented and development-validated. This delivers the background embedding queue, worker admission and workspace progress portion of the [general video plan](GENERAL_VIDEO_IMPLEMENTATION_PLAN.md). Cross-process resource budgets, sustained-load qualification and independent generic-video acceptance remain outstanding.

## Resulting workflow

Complete a recording, select it in **Video memory**, then choose **Prepare this recording**. The server submits all of that recording's retained intervals to a durable worker task. The page shows actual completed/failed counts, cancellation and resume/retry. Closing the page does not cancel the task. Questions can still search directly; any missing representations are generated by the existing query path and coverage/fallback notes remain visible.

Preparation moves clip embedding before the question; it does not eliminate its compute cost or establish that a scene/action was understood correctly. No frame budget, image transform, model revision, tensor precision, vector policy, reranking or claim-verification rule is reduced or replaced. The legacy vector policy remains default and canonical vectors remain a separate opt-in experiment.

## Implementation and integrity

`tools/workflow_indexing.py` owns durable task metadata in `index-jobs-<vector-policy>-v1.sqlite3`. States are `queued`, `running`, `completed`, `failed` and `cancelled`. Each interval records its source hash, source bounds, versioned artifact key, progress and bounded attempt count. Stable task IDs include recording scope, retained source identity, intervals, resolved embedding configuration and vector policy. Reordering the same event set or submitting it twice returns the same task.

Embeddings continue to use the existing versioned vector database and exact JSON representation. Each vector commit precedes its progress marker. A crash between those commits can recover the vector instead of repeating inference. A worker restart requeues interrupted work, preserves completed intervals and leaves cancelled/failed jobs explicit. Retries use the configured budget; an explicit user retry renews the failed/pending work's budget while preserving successful intervals. Repeated missing-source failures also exhaust their budget when a prior vector exists.

The worker revalidates source bytes before writing a newly generated vector and checks source/profile/artifact validity before marking the task complete. Changed sources or model profiles cannot silently complete old tasks. A new preparation request creates the appropriate new task. Checking a completed task again requeues missing or corrupt artifacts. A saved complete marker describes the committed snapshot, not an ongoing guarantee against later source/cache edits; query-time source validation remains active.

Cancellation is cooperative: it prevents further scheduling and a completed-job marker, but an interval already executing may finish and leave a reusable, valid artifact. It does not interrupt an accelerator kernel or delete evidence. Resume continues unfinished intervals. Error details retained in progress are bounded and omit filesystem paths; worker logs contain the diagnosis.

Task metadata uses short-lived SQLite connections. All model operations, source registries, work caches and the existing vector connection are serialized through one inference gate. A process file lock prevents a second task owner from recovering the same policy/database concurrently. The local implementation uses standard-library SQLite, threading and POSIX file locking; no broker/database service or new package dependency was added.

The Rust API builds interval payloads from stored recording evidence instead of accepting client-provided paths. Job controls check recording scope and preserve worker response statuses. Polling does not clone full camera histories. Older query clients and recording schemas remain compatible.

## Scheduling and limits

| Setting | Default | Behavior |
| --- | --- | --- |
| Active Python inference | 1 | Shared by search, interpretation, preparation submission and background clip work |
| `--interactive-queue-limit` | 8 | Maximum waiting interactive requests, in addition to the active operation |
| `--interactive-wait-secs` | 120 | Maximum admission wait; accepts 0..300 seconds |
| `--index-queue-limit` | 8 | Maximum unfinished background jobs, including running jobs |
| `--index-max-attempts` | 2 | Bounded interval attempts; accepts 1..5 |
| Interactive burst | 4 | Give a waiting background unit a turn after at most four admitted interactive operations |

Queue limits accept 1..64. Interactive work is FIFO within its class and normally takes priority. Background work yields between clips, and jobs rotate by their last dispatch. An active clip or question is not preempted; these are admission limits, not guaranteed response deadlines. One unusually long question can still delay other work.

Full background queues return 429; full/timed-out interactive admission returns 503. The worker supplies `Retry-After: 2`. Rust forwards the HTTP status and JSON body for preparation controls; the query endpoint retains its explicit keyword-fallback behavior if semantic admission fails. No overload path silently lowers image quality, drops requested intervals or disables verification.

`/health` exposes the active class, waiting counts, limit and scheduling policy without loading model weights. Detailed telemetry remains opt-in. Interactive admission duration is now actual queue wait; background units emit final traces with task IDs. Failed units have error status. The workspace polls queue/progress separately from the question, so the visible retrieval mode continues to describe what actually ran.

This is **one worker's inference scheduler**. It does not enforce a global memory-byte budget across Rust detector workers, other Python workers or external model servers. The existing Rust media gates remain unchanged. Use one inference worker per device for the evaluated configuration; cross-process coordination and detector/query/index load tests are the next P1 work, before capacity claims or broad rollout.

## API and user controls

| Application endpoint | Purpose |
| --- | --- |
| `POST /api/v1/memory-jobs/{recording}/visual-index` | Submit/check preparation for all stored intervals of a completed recording |
| `GET /api/v1/memory-jobs/{recording}/visual-index` | Return scoped task history and scheduler state |
| `POST /api/v1/memory-jobs/{recording}/visual-index/{task}/cancel` | Cancel that recording's task |
| `POST /api/v1/memory-jobs/{recording}/visual-index/{task}/retry` | Resume cancelled/failed work |

The corresponding loopback worker endpoints are `POST /index-jobs`, `GET /index-jobs?scope_id=...`, `GET /index-jobs/{task}` and the `/cancel` and `/retry` POST actions. Worker submissions require `scope_id` plus 1..10,000 distinct events with IDs, local source paths and millisecond bounds. Paths must be under the worker data root. The request body limit remains 8 MiB.

Responses include `id`, `scope_id`, `status`, `total`, `completed`, `failed`, `pending`, bounded `item_errors`, embedding configuration, vector policy and coverage semantics. `profile_current` is true/false once the worker's current embedding profile is resolved, otherwise null. A completed task under a different or unresolved profile is labeled in the UI; **Check preparation again** resolves/checks the current profile without requiring weight inference on valid artifacts.

Tasks are explicit rather than automatically submitted during recording. Source retention/observer completion and visual preparation are separate states. Search remains available before preparation finishes and shows actual coverage. The surrounding coffee/cream theme is retained; new controls use semantic status text, native progress, keyboard buttons and responsive wrapping.

## Validation

Final validation uses the retained three-camera development footage in isolated output directories. Original sources, annotations, profiles and requests are fingerprint-checked. The frozen pre-package worker and updated worker run sequentially with the same Qwen3-VL Embedding-2B and Reranker-2B revisions, MPS precision and eight 256-pixel frames used in package 3.

| Check | Result |
| --- | --- |
| Unit suite | 97 Python tests, including ten new durable-job/admission tests; 30 Rust tests pass, with two unchanged benchmark tests excluded from the default suite |
| Numerical parity | Four actual paired retrieval responses retain exact scores, ordering and non-diagnostic model/settings proof; all four persisted vectors match exact key/version/JSON values |
| Worker interruption | Kill after 1/4 intervals committed, restart and complete 4/4 with durable progress preserved |
| Browser journey | Prepare another recording, cancel by keyboard, reload, resume, finish 4/4 and obtain real Qwen-reranked search results with four cached embeddings |
| Partial failure | An explicitly synthetic out-of-range interval in isolated metadata produces 1/2 successful, 1 failed; UI reports incomplete coverage and offers retry |
| Evidence/UI | Native video metadata loads; a separate playback smoke check decodes frames and advances playback; final embedded assets match source bytes; no browser script errors or horizontal overflow at 320, 768, 1024 and 1440 pixels |
| Concurrent work | Background preparation, retrieval and pinned sequence interpretation share admission successfully; the unchanged static-evidence guard returns uncertainty |
| Rust restart/scope | Completed preparation remains visible after an independent Rust restart; cross-recording task actions are rejected |
| Queued-work rollback | Frozen older worker preserves exact query output and leaves a queued task untouched; restoring the current worker completes it with all 13 vector rows unchanged |
| Worker unavailable | Preparation controls return 503; normal queries explicitly disclose keyword fallback |
| Fault contracts | Duplicate submissions, queue overflow, invalid requests, owner exclusion, source/profile changes, mutation during inference, missing artifacts, crash after vector commit, bounded retry and cancellation are tested |

Three ordinary recording jobs prepare **13 retained intervals**. The extra invalid-interval fixture is an error-handling control, not an accuracy sample or a fourth independent source. The concurrent eight-millisecond repeated-frame interpretation is a scheduling/static-safeguard control, not evidence of action recognition. No generic-video/action accuracy improvement or sustained capacity qualification is claimed.

Exact comparisons normalize only the existing named cache/timing/policy/telemetry diagnostics; no scores are rounded. The legacy policy's known fresh-versus-cached renormalization behavior remains unchanged. The four actual compared vectors also pass the first-request versus prepared-request comparison; this does not resolve or disprove that known issue on other vectors.

The timing logs retain query and preparation costs separately. Moving work before a question is useful operationally, but the small sequential replay is not a randomized efficiency benchmark. No compute-saving percentage, end-to-end speedup guarantee or memory-byte reduction is claimed. Host/accelerator resource limits from package 3 still apply; Linux/NVIDIA runtime and multi-stream contention remain untested.

## Decision, rollback and next work

Keep the explicit preparation feature and bounded single-worker admission. Existing direct-search behavior and inference profiles remain available. Stop the current worker before rolling back this package's API/UI and worker orchestration together using the saved baseline; retain task/vector databases, source evidence and labels. The older worker ignores the separate task database and can use the same vector artifacts. Restarting the new worker later resumes queued compatible tasks; cancel them before switching if that is not intended. `--interactive-wait-secs 0` restores immediate busy rejection without removing the task feature.

Next P1 package: coordinate resource ownership across detector/retrieval/interpretation processes and run concurrent/sustained load and overload-recovery tests. Qualify cleanup changes only with measurements and preserved safeguards. Then proceed to grouped decoding under P2. Add automatic post-recording preparation only with explicit durable submission/retry behavior and resource coordination. Independent general-video acquisition/review continues alongside engineering; the development corpus still does not satisfy P0 generic acceptance.
